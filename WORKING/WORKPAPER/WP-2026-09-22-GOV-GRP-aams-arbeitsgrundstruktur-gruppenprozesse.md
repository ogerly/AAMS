## 4. Analyse: Real Life Netzwerk · Organisationsmodell

| Dimension | Befund (aus Rohquelle) |
|---|---|
| **Struktur** | Zwei Ebenen: (1) freies offenes **Netzwerk** (offene Grenze, „Schwelle: Ankommen", Spiel-Ebene Level 0→1) + (2) verbindliche **Organisation** im Kern aus **gekoppelten Kreisen** (Entwicklung, Onboarding, Kommunikation). Organisationen = „nichts als ihre gekoppelten Kreise und das gemeinsame Versprechen". |
| **Einheit** | Der **Kreis**: Gruppe mit gemeinsamem Zweck, entscheidet selbst, wie er arbeitet. Zwei Arten: **autonom** (eigener Zweck/Regeln, nutzt Werkzeuge frei — „mehr Verbindung braucht es nicht") und **gekoppelt** (gemeinsames Ganzes, abgestimmte Rollen). |
| **Kopplung** | Kein Raum, keine Ebene über den Kreisen. **Kopplung besteht aus Menschen**: wer in zwei Kreisen ist, trägt Wissen/Bedürfnisse/Ergebnisse hinüber. Tragfähigkeit: **Zwei Schultern** (≥2 gemeinsame Menschen pro Kreis-Paar) + **Anwesenheit statt Amt** (keine Vorgesetzten/Delegierten). |
| **Wachstum** | **Zellteilung** bei >7 Menschen: Kreis teilt sich in zwei Kreise mit je eigenem Thema; die in beiden verbleibenden Menschen sind die Kopplung „vom ersten Moment an". Real Life Stack spiegelt das bereits (mehrere Spaces = gemeinsame übereinandergelegte Sicht). |
| **Anti-Hierarchie** | Drei Leitplanken: **Kein Durchgriff** (Ursprungskreis darf nichts Unkonsentiertes), **freier Exit** (sich lösen/eigenständig/andernorts ankoppeln), **Kopplung statt Befehl** (miteinander über gemeinsame Menschen + Konsent, nie übereinander). |
| **Rollen** | **Focalizer (Pate)**: übernimmt **Verantwortung dafür, dass es passiert** — nicht die Arbeit selbst. Bündelt, behält Überblick, delegiert (an Kreis oder Netzwerk). „Die Rolle garantiert, dass etwas passiert — nicht, wer es tut." |
| **Onboarding** | Spielerisch, wachsend durch Tun (Level 0→1), Einladung durch echte Begegnung. |
| **Öffnung** | Bestandsnetzwerke (Artabana, Coop-Kreise) ragen über den Rand: Hauptleben außerhalb, Netzwerk wirkt **durch sie hindurch**. |

### 4.1 Gap-Analyse: Was das Modell nicht beantwortet

Das Modell regelt **Wer–Wer** (Kopplung, Rollen, Konsent) hervorragend. Es regelt aber **nicht** die Persistenz:

| Situation im Modell | Was heute fehlt |
|---|---|
| Gemeinsamer Mensch pausiert/vergisst/außer Kraft | **Zwei Schultern** retten nur, wenn die andere Schulter es **weiß**. Wissen lebt in Köpfen — nicht auditierbar, nicht übertragbar. |
| Kreis teilt sich (Zellteilung) | Die neuen Kreise sind „vom ersten Moment an gekoppelt" — aber **welche Entscheidungen, Regeln und Kontexte** der Mutter-Kreis gehören zum Start? Im Modell: implizit „die Menschen wissen es". |
| Kreis löst sich (freier Exit) | Was passiert mit dem gemeinsamen Wissen? Im Modell: offen. (Gefahr: Exit = Amnesie für den Verbleibenden.) |
| Focalizer „behält den Überblick" | Überblick ist heute **kognitive Last auf einer Person** — nicht abfragbar, nicht delegierbar, nicht überlebensfähig (Pate fällt aus?). |
| Neue Person „ankommt" (Schwelle: Ankommen) | Onboarding = Begegnung + Spiel. **Wo findet die neue Person die Wahrheit des Kreises**, wenn niemand sie mündlich weiterträgt? |
| Autonome Kreise mit **autonomen Agenten** (User-Kontext: autonome Gruppen) | Kopplung „ist ein Mensch" — Agenten teilen **keine** Köpfe. Ohne gemeinsames Medium können autonome Agenten-Kreise weder koppeln noch Entscheidungen teilen. |

**Kernaussage:** Das Modell hat die **Kopplung** (Wer trägt was wem hinüber) gelöst, aber nicht das **Gedächtnis** (wo bleibt es, wenn die Träger fehlen). Genau da setzt AAMS an — es ist kein Widerspruch zum Kreis-Modell, sondern dessen **Gedächtnis-Substrat**.

## 5. Argumente: AAMS als Arbeitsgrundstruktur für autonome Gruppen

> Kernthese: **Autonomie ohne Gedächtnis ist Verlust.** AAMS macht den Dateibaum zum gemeinsamen Gedächtnis — jeder Agent bleibt autonom in seiner Ausführung, aber die Wahrheit ist geteilt, persistent, prüfbar.

### 5.1 Entscheidungen gehen nicht verloren (Kernargument)

| AAMS-Mechanik | Gruppendienstleistung |
|---|---|
| **Decision-Promotion** (WP → Whitepaper → LTM, READ-AGENT Session-Ende) | Eine Entscheidung lebt nicht im Chat-Context, sondern in der **stabilen Schicht**. Neue Agenten/Gruppenmitglieder lesen sie, statt sie zu raten. |
| **File Protocol** (pro Workpaper: created/modified/moved/deleted) | Jeder Schritt ist **rekonstruierbar** — wer hat was wann geändert, nachvollziehbar ohne Chat-Verlauf. |
| **State Recovery** („File system and git log are ground truth") | In-memory-Task-State ist advisory; Disk ist Wahrheit. Agent stirbt, Session endet, Context läuft über → **nichts geht verloren**. |
| **LTM / MEMORY** (ltm-index.md, Track A = markdown, zero-deps) | Cross-Session-Wissen in einem lesbaren Index — kein Vektor-Store, kein Lock-in, jede Gruppe liest mit. |

### 5.2 Souveränität & Eigenständigkeit

| AAMS-Mechanik | Gruppendienstleistung |
|---|---|
| **Tool-agnostisch** (Manifest-Prinzip D9: beschreibt, schreibt nichts vor) | Jeder Agent nutzt sein eigenes Tool (Claude, OpenCode, Cursor, lokale LLMs) — die **Gemeinsamkeit ist die Struktur, nicht der Vendor**. Kein Lock-in. |
| **Lokalfähig** (`.agent.json` zero-dependency; LTM Track A ohne Python) | Läuft über MANTIS-Proxy + lokale Modelle → **Daten verlassen die Maschine nicht** (Data-Sovereignty, siehe auch UC6 Data-Minimization, WP-013). |
| **Idempotent, drop-in** (ein File `.agent.json` + READ-AGENT.md) | Neue Gruppe/Repo = Bootstrap in Minuten; kein Zentral-System, kein Server, keine Berechtigungs-Hierarchie. |
| **Guard-Pattern** (WH-009, Zwei-Ebenen: AAMS=WHAT, Tool=HOW) | Jede Gruppe erzwingt denselben Vertrag mit ihren eigenen Mitteln (OpenCode-Plugin, Cursor-Rules, …) — **dezentrale Einhaltung, gemeinsame Regel**. |

### 5.3 Autonomie mit Ordnung (keine Chaos-Schwemme)

| AAMS-Mechanik | Gruppendienstleistung |
|---|---|
| **Workpaper-Lifecycle** (active → observe → closed) + **Max-5-Regel** | Begrenzter, indexierter Arbeitsraum. „observe" ist exakt das Warte-Zustands-Bit für „warten auf Gruppen-Entscheidung" — sichtbar, nicht vergessen. |
| **INDEX.md-Pflege** (Whitepaper + Workpaper) | Neuankunft (Agent oder Mensch) orientiert sich in O(1) über den Index — muss nicht alles lesen. |
| **RFL** (3-Stage-Konsistenz-Check) | Agenten **widersprechen sich nicht stillschweigend**: vor neuer Arbeit wird geprüft, ob eine alte Decision dagegen steht → Konsistenzflag statt Silent-Divergence. |
| **Diary** (pointer-only Zeitindex) | „Wann wurde zuletzt an X gearbeitet?" — Antwortbar ohne Content-Duplikate; Audit-Faden über Wochen. |
| **Secrets-Policy** (nie in WP/WH/MEMORY/Manifest) | Gruppenarbeit leakt keine Keys — gerade bei autonomen, parallelen Agenten das Grundrisiko. |

### 5.4 Übersetzung: Agenten-Gruppe ↔ AAMS-Struktur

| Gruppen-Begriff | AAMS-Gegenstück |
|---|---|
| Ein autonomer Agent / eine Session | ein **Workpaper** (eigene Arbeit, eigenes File Protocol) |
| Geteilte Wahrheit der Gruppe | **WHITEPAPER/** (stabil) + **MEMORY/** (gelernt) |
| Entscheidung der Gruppe | **Decision-Promotion** → Whitepaper + LTM-Eintrag |
| Warten auf externes Input | **observe/** (z. B. dieses WP auf das Artefakt) |
| Handover / Neueinrichtung | `on_session_start`: Vertrag lesen → MEMORY query → RFL → Workpaper öffnen |
| Konflikt zweier Agenten | RFL-Consistency-Flag + Git als Schlichter (State Recovery) |
| Audit „Was ist passiert?" | File Protocols + Diary + Git-Log |

### 5.5 Gegenargumente & Antworten (ehrliche Bilanz)

| Einwand | Antwort |
|---|---|
| **Overhead:** Struktur kostet Tokens/Zeit pro Session | Bootstrap ist idempotent + minimal (Track A markdown-only); Kosten << Kosten verlorenener Entscheidungen (Erfahrung aus WP-2026-04-29: Health-Score sank, als Struktur fehlte) |
| **Disziplin:** Agenten folgen Verträgen nicht zuverlässig | Guard-Pattern (WH-009) erzwingt `manifest_read` + `workpaper_open` vor Writes; AGENTS.md + READ-AGENT.md als Eingangstor; Rest = Beobachtung über closed/ |
| **Parallelität:** Zwei Agenten schreiben gleichzeitig | Single-Writer pro Artefakt (Prinzip aus WP-012 Hermes-Local); Git als Schlichter; observe/-Status für „in Diskussion" |
| **Zu viel für kleine Aufgaben** | AAMS skaliert runter: kleine Task = kurzes WP; die Schichten sind Konvention, kein Zwang (D9) |

### 5.6 AAMS als Gedächtnis-Substrat des Kreis-Modells (spezifisch für das Real Life Netzwerk)

> Kernaussage: **Kopplung sind Menschen. Gedächtnis muss Struktur sein.** — Die beiden konkurrieren nicht; sie ergänzen sich.

| Kreis-Modell | AAMS | Was es bringt |
|---|---|---|
| Kopplung ist ein Mensch (trägt hinüber, „was der andere Kreis wissen sollte") | Workpaper/Whitepaper = das **getragene Inhalt**: der gemeinsame Mensch trägt nicht mehr Wissen im Kopf, er verweist auf es | Der Kopplungskanal wird inhaltsarm → weniger Fehlerfläche, kein „Falsch-Weitertragen" |
| Zwei Schultern (Redundanz durch Menschen) | **Dritte Schulter = Dateisystem** (Whitepaper + LTM) | Inhalt überlebt ohne Schultern (Pause, Exit, Vergessen) |
| Anwesenheit statt Amt | Guard-Prinzip: Anwesenheit = Vertrag gelesen (`manifest_read`); keine Rolle nötig, um mitzuwirken | Das eigene Prinzip des Modells, technisch machbar |
| Kein Durchgriff | Keine Admin-Ebene in der AAMS-Struktur; jeder Kreis regelt sich über seine `.agent.json`; Koordination = gemeinsame Artefakte + Konsent | „Kein Durchgriff" per Struktur, nicht nur per Versprechen |
| Freier Exit | Arbeitsgrundstruktur ist das **eigene** Gut des Kreises (portabler Ordner + git) — Exit = Ordner mitnehmen | Exit ≠ Amnesie; das Netzwerk wirkt „durch sie hindurch" — mit ihrer Wahrheit dabei |
| Zellteilung (>7 → zwei Kreise) | **Erbfolge:** der Kind-Kreis startet mit Whitepapers + relevanten Workpapers des Mutter-Kreises (Kopie/Verweis) | Die neuen Kreise sind „vom ersten Moment an gekoppelt" — per Dateien, nicht nur per Menschen-Gedächtnis |
| Focalizer „behält den Überblick" | INDEX + Diary + LTM + `wiki_lint.py` = **abfragbarer Überblick** | Überblick ist keine Kognitions-Last mehr; der Pate kann auch den Überblick delegieren (an die Struktur) |
| Onboarding („Schwelle: Ankommen", Level 0→1) | `on_first_entry`: idempotenter Drop-in → INDEX lesen → erstes Workpaper = „wachsen durch das, was man tut" | Digitales Zwilling-Onboarding, ohne zusätzliches System |
| „Das Werkzeug hat dieselbe Struktur wie das Netzwerk" (Real Life Stack, Multi-Space) | AAMS-Discovery: `WORKSPACE/WORKING` — mehrere Kreise = mehrere effektive Workspaces, **dasselbe** Contract in jedem | Die Struktur des Tools = die Struktur des Netzwerks — bereits in AAMS gebaut |

**Für autonome Agenten-Kreise (Kernfrage des Users):** Menschen koppeln über Anwesenheit, Agenten koppeln über **Dateien**. AAMS ist daher für autonome Gruppen keine Option, sondern **Voraussetzung**:

1. Autonomer Agenten-Kreis = jeder Agent arbeitet in seinem Workpaper (Autonomie), gemeinsame Wahrheit = Whitepaper + MEMORY des Kreises (Gemeinsamkeit).
2. Agent beendet Session → nichts verloren (State Recovery). Mensch verlässt Kreis → die Grundstruktur bleibt.
3. Kopplung zwischen Agenten-Kreisen = geteilte Arbeitsgrundstruktur (ein geteiltes git-Repo pro Organisation = das „gemeinsame Ganze").
4. Focalizer-Garantie („dass etwas passiert") wird **sichtbar**: offene Workpapers + `observe/` = der sichtbare Pflichtenbestand des Kreises — niemand kann stillschweigend vergessen, was versprochen wurde.

## 6. Vorschlag: Erklärung für die Gruppe (10-Minuten-Version)

1. **Ein Satz:** „AAMS ist eine Arbeitsgrundstruktur: jeder Agent arbeitet eigenständig, aber die Wahrheit liegt auf der Festplatte — nicht im Chat."
2. **Eine Datei:** `.agent.json` + `READ-AGENT.md` = der Vertrag (drop-in, idempotent, kein Vendor).
3. **Vier Schichten:** Workpaper (jetzt) · Whitepaper (Wahrheit) · Diary (wann) · Memory (gelernt).
4. **Eine Regel gegen Verlust:** Decision-Promotion — keine Entscheidung stirbt im Context.
5. **Eine Regel gegen Chaos:** Lifecycle (active/observe/closed) + Max-5 + INDEX.
6. **Eine Regel gegen Widersprüche:** RFL-Konsistenz-Check vor neuer Arbeit.
7. **Souveränität:** tool-agnostisch, lokal lauffähig (MANTIS-Proxy), keine Cloud-Pflicht, Secrets-Policy.
8. **Beweis aus der Praxis:** dieses Repo — 10 Whitepapers, 66+ Workpapers, 148 LTM-Einträge, Health-Check via `wiki_lint.py`, Upgrade-System 2.4.0 — alles auditierbar, nichts verloren.
9. **Für euer Modell konkret:** „Eure Organisation ist nichts als ihre gekoppelten Kreise und das gemeinsame Versprechen." — **AAMS ist dieses gemeinsame Versprechen materiell:** die Garantie, dass keine Entscheidung stirbt, wenn Menschen pausieren, Kreise sich teilen oder sich lösen. Eure Leitplanken (Kein Durchgriff, freier Exit, Kopplung statt Befehl) sind in AAMS strukturell abbildbar (§5.6).
